# Host probes P1, P3, P4, P5, P7 to P9

Scripts for the probes of `docs/design/probes.md` section 2 that can run before any makiba code exists. A person runs them on a real host, from a login shell, never from inside an agent or CI. Nothing here has been run yet: the scripts were written in a sandbox that cannot start herdr-core.

Not here: **P2** (needs a GitHub repository, see probes.md) and **P6** (needs a secretary, M6-2).

## Before running

- Needs `bash`, `python3`, `git`, `claude` (logged in) and `hc`. Each script takes the base binary from `HC_BIN` (default `hc`), prints `hc --version` and `claude --version` first, and records them in the result file.
- The design reads herdr-core 0.1.21. If `hc` on PATH is older, install 0.1.21 beside it, without replacing the one you use, and point the probe at it: `HC_BIN=/path/to/hc-0.1.21 bash scripts/probes/p3-send-waits-for-draft.sh ./results`. Do not run `hc update` on the binary you use: it replaces it (`hc update --version X|--from <file>` is in `hc --help`). How to obtain a separate 0.1.21 binary was not checked here; any way that leaves your own `hc` in place will do, and the script refuses P3 below 0.1.20 either way.
- Every run uses its own core: `HC_SESSION=makiba-probe-<pid>`, scratch `XDG_CONFIG_HOME` and `XDG_STATE_HOME`, and stops only that core at the end, also on failure. The variables of spec section 6.4 are removed first. No real secret is used; P1 writes a decoy.
- Claude Code's own trust record in `~/.claude.json` is shared (as with any accepted dialog): P3, P4 and P5 add entries for their scratch repositories.
- Each script takes one argument, the directory for the result file `<probe>-result.txt` (versions, date, script commit, one line per case, captured screen text on failure). Every case prints `CASE <name>: PASS|FAIL|NEEDS-HUMAN`. Paste the result file into probes.md section 1 with the versions.

## P1 `p1-door-reach.sh <dir>`

Runs a small Unix-socket listener at a door path, builds worker settings (sandbox on, door allowed, the scratch core's socket and state folders denied, no deny rule and no hook for `hc`), launches a worker and has it run five commands, one Bash call each: connect to the door, connect to each of the base's socket paths, `hc ls`, `cat` of a decoy under the state folder. The commands live in `c1.sh` to `c5.sh` in the worker folder and write their own exit code and output to `report.txt`.

Pass: `door-reachable` PASS, and `base-socket-*`, `hc-ls`, `state-decoy-read` PASS (each failed with a sandbox-style error, not a deny-rule refusal). NEEDS-HUMAN means the error text was not recognised or the call never ran: read the captured screen.

## P3 `p3-send-waits-for-draft.sh <dir>`

Refuses to run (exit 3, `REFUSED`) on hc below 0.1.20. Types `half typed` without Enter, sends the wrapped message from a background shell, looks at the screen after 20 s, presses Enter, and checks that `half typed` is one prompt and the wrapped text the next.

- Default `P3_MODE=keys`: the draft is typed with `hc keys`. This **stands in for a person**; whether the base counts keys as a person's typing is unmeasured, so a PASS here is weaker than a human run. The result file says so.
- `P3_MODE=human`: the script prints an `hc attach` command with the right session; you type `half typed` in it, press Enter in the script's shell, and later press Enter in the attached terminal when asked.

Pass: `send-held-20s` PASS and `order-after-enter` PASS.

## P4 `p4-delivery-text.sh <dir>`

Eight cases to one idle Claude Code (acceptEdits mode, in a scratch repository): a 12-line body, a 4000-character body, first lines `/clear`, `!ls`, `#note`, a body with the closing tag (escaped as in spec section 8), two wrapped messages in one send, two sends back to back. The agent is told to write each body to `echo-<id>.txt`; the script compares the file with what was sent. "No line acts as a command" is inferred from that file coming out whole; "one prompt" is checked by counting prompt lines that start with the wrapper in the screen history (more than expected is a FAIL, fewer is NEEDS-HUMAN).

Pass: all eight PASS. A failing case is a shape that must never be typed (M2-4). The "terminal read as `done` that starts a turn in the same second" case is approximated by the two quick sends.

## P5 `p5-launch-task.sh <dir>`

Fresh git repository nobody trusted; `claude` launched through the base with the task as its last argument; the trust dialog is passed by the folder-trust policy (cursor moved onto a Yes line, screen read again, one key); `hc send` is never called. Pass: the reply to the task appears (`task-after-dialog` PASS). NEEDS-HUMAN with "no trust dialog" means the folder was already trusted and the case did not run.

## P8 `p8-channel-delivery.sh <dir>` and P9 `p9-mcp-from-sandbox.sh <dir>` (channel candidate)

Measure the design's new first candidate: an agent asks a resident program through an MCP tool, and the program delivers text through a Claude Code channel (`notifications/claude/channel`), typing into the terminal only as a fallback. `makibad` does not exist, so `channel-standin.py` (python3 standard library, no import from claude-org-runtime) plays it: an HTTP MCP server on 127.0.0.1 (`send_request` tool, bearer token) and a stdio channel server. Message shapes were read from claude-org-runtime (`broker/server.py`, `broker/channel_sidecar.py`, `broker/tokens.py`) and launch arguments from `claude-org-ja/.dispatcher/references/spawn-flow.md` 3-2 / 3-3b: `--mcp-config <json|file>` carrying the http server and the stdio channel server, plus `--dangerously-load-development-channels server:makiba-channel`. `dialog-step.py` is the startup-dialog policy (option text matched whole, cursor moved, screen read again, one key); dialog screens are written to the result file.

P8 cases: `dev-channel-dialog`, `turn-start-visible` (seconds from enqueue to a state or turn change in `hc get --json`; paired with `turn-start-unchanged-without-delivery`, where the stand-in holds the message back), `channel-while-working` (a message sent in the middle of a `sleep 45` turn: PASS means delivered, the detail says whether it acted before or after the turn's end; FAIL means lost). `channel-to-done` (one notification to a target that reads `done`: seconds to a state or turn change), `channel-while-done` (the text appears once), `turn-start-for-another-cause` (stand-in paused, a typed line starts the turn: PASS means the turn start was seen and the held message was not delivered, so status alone cannot tell the two apart), `two-in-a-row` (two notifications back to back: each once, which first), `channel-while-blocked` (a permission prompt opened by a command the agent settings do not allow; a notification is sent while the base reads `blocked`, the prompt is answered with the one-time yes only afterwards; records when the text appeared, how often, and the status). Cases that cannot decide end in NEEDS-HUMAN with the screen text. Every case starts from a verified resting state (idle or done, the same state and turn over four samples, nothing queued in the stand-in; a stray permission prompt is declined with Escape first) and ends in NEEDS-HUMAN when that state is not reached. Waits are wall-clock deadlines (`P8_TIMEOUT_SCALE=2` doubles them), every `hc` call is bounded by `timeout` (`HC_CALL_TIMEOUT`, default 60 s), and the result file says in which step a run that stopped early ended. `channel-while-working` uses a turn of twenty Write calls, because Claude Code refuses a foreground `sleep 45`; the text is counted from channel header lines (`← makiba-channel: PROBE-MSG <id>:`) in one captured history. `channel-while-draft` is not measured: the owner reports that channel text never mixed into a person's draft in claude-org-ja.

P10 open steps (the same script, after the cases above): `resume-dialogs`, `resume-ready`, `renewal-dialogs`, `renewal-ready`. The first agent is ended (`hc kill`, then `hc rm`), then a new terminal is launched in the same scratch repository, which the first launch already trusted. Resume: `claude --resume <session-id>` with the same channel flags; the first launch is given `--session-id <uuid>` (only when `claude --help` names it) so the id is known. Renewal: a new session, no resume, the same channel flags (what renewing the secretary does). Every dialog goes through the same policy as the first launch (`pass_dialogs`, cursor read again before the key; screens with their option lines go to the result file), run once more after 6 s so a late dialog is not missed. Dialog cases: PASS = every dialog shown was folder-trust or development-channel and was passed by the policy (also PASS when none appeared, and the detail says so, with which came back and in which order); FAIL = a known dialog was not passed; NEEDS-HUMAN = a dialog that is not one of the two (not answered, screen in the result file) or no usable screen. Ready cases: PASS = the base reports a resting state (`idle` or `done`) with no dialog on screen (the trust dialog is not answered silently there); a resume also needs lines of the first session in the history, otherwise NEEDS-HUMAN, because a fresh session cannot be told from a resumed one. The result file records the option used, the matching `claude --help` lines and `claude --version`. If `claude --help` names no `--session-id`, the resume cases are NEEDS-HUMAN and the renewal cases still run. Not covered: a task as the last argument of these launches (P10 step 1 mentions one; the first launch of this script has none, as before), and the exact-label strictness of the policy (`dialog-step.py` matches option labels by prefix).

P9 cases (sandbox on, no network allowance; a second agent runs beside the sandboxed one): `mcp-tool-reaches` (the tool call arrives); `bash-http-direct` (urllib with `ProxyHandler({})`) and `bash-http-via-default-proxy` (urllib defaults, proxy variables honoured), each recording one line `type= errno= reason= msg= proxyvars=` (PASS = blocked with a network-style error, nothing logged by the stand-in, listener alive from outside; FAIL = it got through, the token is then the only guard); `own-token-env`, `own-token-argv`, `own-token-file` (this session's decoys: env variable, `--mcp-config` argv, a file under a `denyRead` path; PASS = Bash cannot find or read it); `other-session-token` (the second agent's env and argv decoys searched in every readable environ and cmdline; the heavier risk); `credential-envvar-unset` (a decoy variable listed in `sandbox.credentials.envVars` with mode deny: is it gone from Bash's own environ?). Locations are reported, never values.

P9 channel-server cases (the gap left by P11, probes.md): the stand-in channel server that Claude Code starts for the session (`makiba-channel`, launched with `--dangerously-load-development-channels`) gets a decoy in the `env` of its MCP entry and a decoy in its `args` (as the value of `--state`, which the stand-in accepts and ignores). The entry sits in a second `--mcp-config` file under a path the worker's settings deny, so the decoys are not in the claude process's own argv. `channel-server-running` is the control, made from outside the sandbox before the prompt and again after the agent's work: the server process runs and its `/proc/<pid>/environ` and `/proc/<pid>/cmdline` hold the decoys (PASS; otherwise NEEDS-HUMAN, and then no "absent" below proves anything). `channel-token-env` and `channel-token-argv`: a fourth sandboxed Bash step (`d.sh`) scans every readable `/proc/*/environ` and `/proc/*/cmdline` and Bash's own environ, reporting locations only (PASS = not found; FAIL = found, the detail says whether the channel server's pid is among the locations). The result file also carries `OBSERVE channel-server-pid-visible-from-bash` (yes, no, or unknown when there was no control pid or no usable step line), with whether Bash could read the server's cmdline and environ. A run that stops before the worker is ready gives all three NEEDS-HUMAN.

Notes: P4 counts submitted prompts without the live composer (the 2026-11-18 zero counts came from a grey suggestion in the composer).

## P1 and P11 again (M4-2) `door-and-base-reach.sh <dir>`

Needs a built `makiba` as well: `cargo build`, then `MAKIBA_BIN=target/debug/makiba MAKIBA_COMMIT=$(git rev-parse --short HEAD) bash scripts/probes/door-and-base-reach.sh ./results`. Unlike the scripts above, it does not write the worker's settings itself: the real `makibad` runs on the probe's own core (`MAKIBA_BASE_SESSION`), with its door on a port of the system's choosing (`MAKIBA_PORT=0`, `MAKIBA_DOOR=none`) and the person key moved by `MAKIBA_PERSON_KEY` to a decoy under the scratch folder. A document run is queued in its scratch `state.db`; `makibad` takes it, writes `<state>/settings/<task>.json`, issues the key and launches the terminal. The agent module is `fake`, the only one `makibad` launches today; `MAKIBA_FAKE_AGENT` points it at a shim that execs `claude` with the `--mcp-config` `makibad` built and `--settings` naming that file, plus `--setting-sources project,local`, `--permission-mode acceptEdits` and `--allowedTools 'Bash(bash:*)'` (the probe's only additions). Startup dialogs are left to `makibad`'s dialog pass for 90 s (`OBSERVE makibad-passed-dialogs`). The settings file goes into the result file; the token never does (only the first digits of its hash).

Outside the scratch folder it writes only `makiba-probe-decoy-<pid>.txt` in `~/.local/state/herdr-core` and `~/.config/herdr-core` (the folders makiba denies are the home's, not `XDG_*`; a folder made for them is removed again) and, only if a call escaped the sandbox, `~/makiba-probe-outside-<pid>.txt`; all are removed at the end.

Cases: `hc-ls` (with the core's session named; the control is that the core lists the worker from outside), `base-socket` (the running core's socket; the line names the refused phase, `socket` when the AF_UNIX socket cannot even be made, `connect` when the path is refused; no traceback is judged, since the fourth host run took a marker quoted in one for a success), `state-decoy-read`, `config-decoy-read`, `person-key-read` (the moved place), `state-db-read`, `proc-keys` (a stand-in secretary's key in its environment and token in its arguments, and the worker's own token by its hash, in every readable `/proc/*/environ` and `cmdline`), `double-fork` (base socket and door port from a grandchild after `setsid`), `port-direct` and `port-via-default-proxy` (HTTP to `makibad`'s port; the control is an answer from outside), `unsandboxed-run` (a Bash call asked to run outside the sandbox tries to write a marker in `$HOME`), `read-tool` and `edit-tool` (the decoy person key), `mcp-json-write` (a Bash write of the workplace's `.mcp.json`, inside the write surface, which the per-task settings deny by its absolute path, Issue 137; asked after the two tools, so a write that gets through cannot change the settings the earlier steps ran under; also a FAIL when the file holds the marker). An OBSERVE line records the same write of `.claude/settings.json` next to it, which makiba does not deny, to show what Claude Code does by default. Claude Code itself denies writes to `.mcp.json` in the working directory by default (its sandboxing documentation, "Protected paths"), so a PASS of `mcp-json-write` shows that the write is refused in the real launch, not which of the two holds it. `PROBE_STEPS="14 15"` asks only the steps named (1 to 15): every case of a step not asked is NOT-RUN, and the SUMMARY says the run was partial and which steps were asked (Issue 137: the model's safeguards stopped full runs 6 and 7 at step 8 and at step 10). The output also goes to `<result-dir>/door-and-base-reach-run.log` as it is printed; `tee` ignores INT and TERM, so a run ended by `timeout` still runs its cleanup and leaves the log. The role hooks in the settings run `<share>/makiba`, which `makibad` links only for agents other than `fake`: when it is missing the probe links it to `MAKIBA_BIN` and removes the link (and the folders it made for it) at the end; run 6 printed a failed hook five times on every Bash call without it. PASS for each means refused: by the sandbox for the Bash cases (a deny-rule refusal is a FAIL there, since the settings have none for these), by a permission rule for the two tools. Each step is its own turn: one short instruction (`Run this one command with the Bash tool ...: bash cN.sh`), then a wait for that step's own result (its STEP line, or `readtool.txt` / `edittool.txt`). A permission prompt is recorded with its screen and declined with Escape, which on Claude Code 2.1.328 also ends the turn; the next step is a fresh message, so only that step is lost, and its case says so. The instruction asks for nothing back but the word done, since asking for the exit code made the agent append an `echo` (a compound command, which raised a prompt in the third host run); a Bash step lost to a prompt is asked once more. The helper scripts avoid standard-library module names (`http.py` shadowed Python's `http` in the third run). A call that only reads a step file writes no STEP line, so it is never taken for the step's result. For the two tools, a prompt that names the decoy is a FAIL (no rule refused it). NEEDS-HUMAN means the step did not run or its text was not recognised. The control from outside the sandbox (an HTTP request and a TCP connect to the port, and whether makibad still runs) is written as its own line. Why per step: the first host run (2026-11-19, Claude Code 2.1.328) sent all steps in one message; the model's safeguards flagged it, the agent read the step files first, that call raised a prompt, and the Escape interrupted the whole turn, so no step ran. The decoy person key is named `decoy-<pid>.txt` for the same reason.

## P7 `p7-user-settings.sh <dir>`

What an agent takes from the person's own Claude Code settings, and whether a worker can notify the person (probes.md P7). Takes about 40 minutes and needs a person at the host, because a script cannot see a phone, a desktop or a bell: watch them while it runs. `P7_NOTIFY_WAIT` (seconds, default 70) is the no-input window after each event; it is long enough for the idle notification, and nothing is typed in it, so a later input cannot cancel the notification being measured.

The person is played by a scratch `HOME`. The script reads the real user-level folder once (`settings.json`, `CLAUDE.md`, `.credentials.json`, `skills`, `commands`, `agents`, `hooks`, and `.claude.json`; symlinks followed) into a scratch copy, merges in four decoys, and launches every `claude` with `HOME` (and `CLAUDE_CONFIG_DIR` where it is the option) below the scratch folder. It refuses a launch that points elsewhere, and the last case checks that the real folder holds no decoy text and did not change. Not copied: plugins, projects, history. A host hook that names an absolute path outside the folder still runs that real file (the result file says which hooks name a path under a user folder; `~` resolves to the scratch home). Read the HOST-NOTIFY lines before you trust a run: they name the notification-like settings and hook events the host has (values only for plain flags; no command text, no secret).

Decoys: a rule line in `CLAUDE.md` (`PROBE-USER-RULE`), hooks on `UserPromptSubmit`, `Stop` and `Notification` that append to marker files, a skill `probe-user-skill`, a user-level connector `probe-user-conn` that writes a marker when started. Each launch is made the way `makibad` would: role rules as an appended file (`ROLE-RULE`, answer ends with `ROLE-OK`), a per-task settings file (role hooks on `UserPromptSubmit`, `Stop`, `Notification` and `InstructionsLoaded` writing marker lines with the hook's input, an `ask` rule for `python3`), and the role's own connector (the stand-in's HTTP server, called once to prove it works). Options, each recorded exactly in the result file with `claude --version`: `plain` (nothing special, the control), `sources` (`--setting-sources project,local`), `sources-strict` (the same plus `--strict-mcp-config`), `configdir` (`CLAUDE_CONFIG_DIR` pointing at an alternate folder holding an empty `settings.json` and a copy of `.credentials.json`, so the login is shared and the connectors are not).

In each run the agent is asked "List every rule, skill, hook and connector you can see." (the answer goes to the result file), then a connector call, then, for worker, curator and the control, three events with UTC timestamps: the turn end, a question (`AskUserQuestion`) and a permission prompt, each followed by the no-input window. Per event the line says whether the role's and the user's `Notification` hooks fired. A decoy "reaches the agent" when its marker exists, the screen shows it, or (the rule) the role's `InstructionsLoaded` hook logged the user-level `CLAUDE.md`.

Cases: `control-plain` (PASS = all four decoys reach the worker with no option and the role's own items apply; otherwise NEEDS-HUMAN and no "absent" below is trusted), `option-sources`, `option-sources-strict`, `option-configdir` (PASS = no decoy reaches the agent while the role's own rule, hook and connector apply; FAIL = the detail names the user-level items that reach agents; NEEDS-HUMAN = no composer, the role's own items missing, or the control did not show an item), `isolation-found` (PASS if any option passed; FAIL only when every option was conclusive and none passed), `curator-isolated` (the first isolating option, launched as a curator), `secretary-decoys` (observation: which decoys reach a secretary under `plain`), `secretary-separate` (a secretary launched under the isolating option beside the isolated worker: its own role items apply, and the worker still shows no decoy after taking a fresh turn), `real-folder-untouched`, and `notify-outside`, which is always NEEDS-HUMAN: compare the EVENT timestamps with what rang on the phone, the desktop and the terminal, per run. P7 passes only if `isolation-found` is PASS and, in the isolating option, nothing outside the terminal rang for a stop, a question or a permission prompt of a worker or the curator.

Not run, and needed only when a case failed (M3-4, M4-3): how the role rules rank against a user-level item that leaks, and switching a notification off through a worker's own settings. The cost of `configdir` (login shared by a file copy, connectors not carried, any onboarding dialog it shows) is in its case line and the dialog screens of the result file.
