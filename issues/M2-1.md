# M2-1 makibad: one instance, a heartbeat, a clean stop

## Before starting

Do not start until probes P1 to P5 and P7 to P11 are recorded as run, with versions and date, in `docs/design/probes.md` (Results). They are run by hand before any Issue of M2 or M3, on the pinned base version. A probe run in part names the steps not run; those are run before the Issue that relies on them lands.

## Why

A dispatcher that silently is not running is the 20-day relay silence again (incident I-3). A dispatcher that says it is ready before it listens is #1168 (I-4).

## What to build

- `makiba/daemon/main.py`: takes `makibad.lock` (flock) or exits; opens `state.db`; connects to the base; establishes the subscription; only then sets `dispatcher.subscribed = 1` and writes `dispatcher_started`.
- Writes `dispatcher.heartbeat_at` every 10 s. On SIGTERM: finishes the current step, writes `dispatcher_stopped`, releases the lock.
- `makiba status` run by the person reads `state.db` read-only itself, with no door, so that it works when `makibad` is dead; it prints the heartbeat's age and whether it is subscribed, and exits non-zero when the heartbeat is older than 30 s. The agent's tool `status` goes through the door (M6-1). The local reader is one module, `makiba/status_local.py`, and the only code of `makiba` that opens the database.

## Not in this Issue

- Starting `makibad` at boot (stage 2).

## Definition of done

The first commit adds `tests/test_heartbeat.py`, failing, with the trailer `Acceptance-Test: tests/test_heartbeat.py`. At head it passes and asserts:

- A second `makibad` on the same state folder exits with a message naming the first one's pid.
- `subscribed` is 0 until the subscription exists (the stand-in delays it) and 1 after.
- After `makibad` is killed with SIGKILL, `makiba status` exits non-zero within 30 s.
