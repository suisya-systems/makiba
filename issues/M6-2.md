# M6-2 Launch the secretary

## Why

The secretary is one more terminal the dispatcher launches, with a fixed name and its own folder.

## What to build

- `makiba up` launches role `secretary` in `<state>/secretary/`, named `secretary`, with its token in the launch arguments, rules file and settings; passes its startup dialogs (folder-trust and the development-channel one) by the policy list.
- If a terminal named `secretary` with the organization's tag already runs, nothing is launched.
- Setting `secretary.remote_control` (default off): when on, the Claude Code agent module adds Claude Code's Remote Control option to the secretary's argv, so the person can reach the secretary from the Claude app. No other role ever gets it and no other module reads the setting (plan.md section 2, probe P6).
- `makiba status` shows how to attach to it.

## Definition of done

The first commit adds `tests/test_secretary_launch.py`, failing, with the trailer `Acceptance-Test: tests/test_secretary_launch.py`. At head it passes and asserts:

- After `up`, one terminal named `secretary` with `makiba.role=secretary` exists.
- A second `up` launches no second one.
- With `secretary.remote_control` on, the secretary's argv carries the Remote Control option and a worker's argv does not; with it off, neither does.
- The secretary's folder holds no file from the makiba checkout that the settings do not name.
