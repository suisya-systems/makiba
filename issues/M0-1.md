## Why

Nothing can be merged test-first until the repository can run a test in CI and say whether a declared test failed at the test commit and passed at head. makiba is written in Rust (plan.md section 5), so that test is a Cargo integration test.

## Definition of done

The first commit adds `tests/test_acceptance_check.py`, failing, with the trailer `Acceptance-Test: tests/test_acceptance_check.py`. At head it passes and asserts:

- In a scratch git repository holding a small Cargo package: a branch whose first commit declares `tests/<name>.rs`, failing by an assertion, and whose head makes it pass yields `ACCEPTANCE: pass`.
- A declared test that does not compile at the test commit (it calls a function head adds) counts as failing there, and the branch yields `ACCEPTANCE: pass` when head passes.
- A declared test file with no `#[test]` at the test commit (`running 0 tests`) yields `ACCEPTANCE: fail`.
- A declared test that already passes at the test commit yields `ACCEPTANCE: fail`.
- A declared test with an `#[ignore]` test at head, or with no test run at head, yields `ACCEPTANCE: fail`.
- A declared path that is not a test target (`tests/common/mod.rs`) yields `ACCEPTANCE: fail`.
- A declared `tests/test_x.py` behaves as before (fails by pytest at the test commit, passes at head).
- A branch with no trailer yields `ACCEPTANCE: none`.

## Notes

Replacement text for `docs/acceptance-check.md`, rule 3 and what it needs:

**Test targets.** A declared path is a test target: a file `tests/<name>.rs` directly under `tests/`, or a folder `tests/<name>/` holding `main.rs` (or that `main.rs` itself); its target name is `<name>`. For the development tools, a file `tests/**/test_*.py` is also a declared test. A declared path that is neither, at the test commit, fails the check. Test helpers are the other files under `tests/` (`tests/common/`, fixtures, the test agent's source): the test commit may add them, and rule 4 protects them.

**How a target runs.** In each of the two worktrees (test commit and head), with `CARGO_TERM_COLOR=never`: `cargo fetch --locked` first, so that a download failure is not mistaken for a test result; then `cargo test --locked --test <name>`, with stdout and stderr kept. With `--test` Cargo builds the library, the binaries and that one test, and runs no other test and no doc test, so the output holds at most one `running N tests` line and one `test result:` line.

**Fails at the test commit** when either holds: (a) the output contains ``error: could not compile `makiba` (test "<name>")``: the test does not compile, as an import error did in Python; only this target, since the test commit changes nothing but tests and the base builds; (b) the output contains `running N tests` with N at least 1 and Cargo exits non-zero (a failed assertion, a panic, or a crash of the test binary). Anything else does not count as failing and fails the check: exit 0 (the test passes), `running 0 tests` (nothing ran, as pytest's exit 5), or a non-zero exit with neither (a fetch, lock-file or library build failure: the check prints the last lines and says it could not run the test).

**Passes at head** only when Cargo exits 0 and the `test result: ok.` line reads P passed, 0 failed and 0 ignored, with P at least 1. An ignored test at head fails the check; so does a target that runs no test.

**A Python test** (`tests/**/test_*.py`) runs as before: `python3 -m pytest <path>` from the tree root; exit 5 (no test collected) is not failing.

**Known limits.** A test that needs a new dev-dependency cannot add it in the test commit (rule 2), so it fails to compile there for that reason and counts as failing; the reviewer sees it in the log. `rust-toolchain.toml` is not protected by rule 4; a change to it after the test commit is a review matter. The others of the current text stay (a pull request without a declaration passes as `none`; the workflow file is read from the pull request).

Branch protection (require `acceptance`, `tests`, `lint`; require branches up to date) is a setting only the owner can make. The checker of the base runs this pull request's own test commit, and that checker runs `tests/test_acceptance_check.py` with pytest, so this rework can go through the acceptance gate.
