# M6-1 The secretary's commands

## Why

The secretary acts through commands that are recorded, not through a terminal.

## What to build

- Verbs `dispatch`, `close`, `answer` (questions; prompts are M6-8), `pr` (wired in M5-3), `pending`, `peek`, `status`, `renew` (wired in M6-5), each checked against the role table of spec section 4.
- The person's `dispatch` reads `--brief-file` itself and sends the content; the tool takes the brief as text. `makibad` never opens a path an agent names.
- `peek` returns the last lines of a worker's screen, read by `makibad`.
- `makiba --help` and per-verb help, generated from one table.

## Definition of done

The first commit adds `tests/test_cli_secretary.py`, failing, with the trailer `Acceptance-Test: tests/test_cli_secretary.py`. At head it passes and asserts:

- Each verb, called as the secretary's tool, is recorded in `commands` and returns a result.
- `dispatch` creates a `queued` run, its `run_launch` row with the brief and the kind, and `delegate_sent`.
- `dispatch --kind code` without `--project` is a usage error; `--kind document` needs none.
- A worker's key cannot `peek` or `dispatch`.
- The tool `status` goes through the door and returns what the person's local `status` returns; the person's `status` is the local read of M2-1.
- Every exit code of spec section 3 is produced by at least one case.
