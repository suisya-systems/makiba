# M0-2 Pin the base's version and the supported Claude Code versions

## Why

herdr-core releases every few days and calls its API a preview. makiba must run against one known version and refuse any other. The pin is not meant to follow the releases: moving it costs a test run and several probes, so it moves on purpose and rarely.

## What to build

- `makiba/base/version.py`: the supported range (`>=0.1.21,<0.1.22`, one patch release; the version the design was read against and the probes of `docs/design/probes.md` are run on) and a check of the version `Base.hello()` returns.
- `scripts/install-base.sh`: installs the pinned release into a given prefix; used by CI and by a person.
- `docs/upgrading-the-base.md`: when the pin moves, and what a move costs. It moves when a release carries something makiba needs, when the pinned release can no longer be installed, or at the owner's monthly look at the base's changelog; not on every release, and not more than about once a month. A move reruns: M1-5's test against the new release's own definition; the whole suite on the stand-in and on the real base; probes P1, P3, P4, P5 and P8 on the new version (they measure how the base is reached, typed into and launched, and how a turn start shows in its status, which a patch release has changed before: 0.1.20 changed sends), each a few hours of the owner's time; P2 reruns itself in CI. A probe may be skipped only when the changelog shows nothing touching its area and the record says so. P6 is not rerun.
- The range stays one patch release. A wider range would let a version in that no probe has run on. It is revisited only after three pin moves in a row needed nothing but the number changed.
- `makiba/agents/version.py`: the supported range of Claude Code and a check of the text `claude --version` prints. The range runs from the lowest to the highest version that a recorded run of the probes covers (the `claude --version` column of `docs/design/probes.md`, Results; paddock's measurements, 2.1.319 to 2.1.322, until the new ones exist), and no wider. It is a separate constant from the base's, because Claude Code is not behind the seam and updates itself.
- `docs/upgrading-claude-code.md`: when the range moves and what a move reruns. Claude Code releases more often than the base, so the range moves only after the owner has rerun the following on the new version: probes P1, P3, P4, P5 and P7 to P11; paddock's carried probes (probes.md section 1); the runbook of M4-5 once; and P6 only when `secretary.remote_control` is on. The startup-dialog and prompt tests of M3-5 and M6-8 use the test agent and cannot show a change in the real screens; these reruns can.

## Definition of done

The first commit adds `tests/test_base_version.py`, failing, with the trailer `Acceptance-Test: tests/test_base_version.py`. At head it passes and asserts:

- A version inside the range is accepted.
- A version outside it raises before any other call is made, with a message naming both versions.
- `docs/upgrading-the-base.md` names M1-5's test file and each of P1, P3, P4, P5 and P8.
- A `claude --version` text inside the range is accepted; one outside it, and one that cannot be parsed, raise with a message naming the version found and the range.
- `docs/upgrading-claude-code.md` names each probe and the runbook listed above.

## Notes

Claude Code's version goes here and not in a new Issue because it is the same kind of pin, kept in the same place and checked by the same kind of test; the check at `makiba up` is M4-4's.
