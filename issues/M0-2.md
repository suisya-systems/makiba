# M0-2 Pin the base's version and the supported Claude Code versions

## Why

herdr-core releases every few days and calls its API a preview. makiba must run against one known version and refuse any other. The pin is not meant to follow the releases: moving it costs a test run and several probes, so it moves on purpose and rarely.

## What to build

- `src/base/version.rs`: the supported range (`>=0.1.21,<0.1.22`, one patch release; the version the design was read against and the probes of `docs/design/probes.md` are run on) and a check of the version `Base::hello()` returns.
- `scripts/install-base.sh`: installs the pinned release into a given prefix; used by CI and by a person. It reads the base's release manifest, `https://releases.herdr.dev/core/<version>/manifest.json` (`HERDR_RELEASES_URL` replaces the host), whose `targets` give a `url` and a `sha256` for each of `linux-x86_64`, `linux-aarch64`, `macos-aarch64`, `macos-x86_64` and `windows-x86_64`. It picks the machine's target (makiba does not run on Windows, so the last is never picked), downloads its `url` with `curl`, and installs nothing unless the file's SHA-256 equals the manifest's.
- `docs/upgrading-the-base.md`: when the pin moves, and what a move costs. It moves when a release carries something makiba needs, when the pinned release can no longer be installed, or at the owner's monthly look at the base's changelog; not on every release, and not more than about once a month. A move reruns: M1-5's test against the new release's own definition; the whole suite on the stand-in and on the real base; probes P1, P3, P4, P5 and P8 on the new version (they measure how the base is reached, typed into and launched, and how a turn start shows in its status, which a patch release has changed before: 0.1.20 changed sends), each a few hours of the owner's time; P2 reruns itself in CI. A probe may be skipped only when the changelog shows nothing touching its area and the record says so. P6 is not rerun.
- The range stays one patch release. A wider range would let a version in that no probe has run on. It is revisited only after three pin moves in a row needed nothing but the number changed.
- `src/agents/version.rs`: the supported range of Claude Code and a check of the text `claude --version` prints. The range runs from the lowest to the highest version that a recorded run of the probes covers (the `claude --version` column of `docs/design/probes.md`, Results; paddock's measurements, 2.1.319 to 2.1.322, until the new ones exist), and no wider. It is a separate constant from the base's, because Claude Code is not behind the seam and updates itself.
- `docs/upgrading-claude-code.md`: when the range moves and what a move reruns. Claude Code releases more often than the base, so the range moves only after the owner has rerun the following on the new version: probes P1, P3, P4, P5 and P7 to P11; paddock's carried probes (probes.md section 1); the runbook of M4-5 once; and P6 only when `secretary.remote_control` is on. The startup-dialog and prompt tests of M3-5 and M6-8 use the test agent and cannot show a change in the real screens; these reruns can.

## Definition of done

The first commit adds `tests/base_version.rs`, failing, with the trailer `Acceptance-Test: tests/base_version.rs`. At head `cargo test --test base_version` passes and asserts:

- A version inside the range is accepted.
- A version outside it is refused (`BaseError::UnsupportedVersion`) before any other call is made, with a message naming both versions.
- `docs/upgrading-the-base.md` names M1-5's test file and each of P1, P3, P4, P5 and P8.
- A `claude --version` text inside the range is accepted; one outside it, and one that cannot be parsed, are refused with a message naming the version found and the range.
- `docs/upgrading-claude-code.md` names each probe and the runbook listed above.
- `scripts/install-base.sh`, with `HERDR_RELEASES_URL` naming a scratch folder that holds a manifest and a file, installs the file when its SHA-256 matches, and installs nothing and exits non-zero when it does not.

## Notes

Claude Code's version goes here and not in a new Issue because it is the same kind of pin, kept in the same place and checked by the same kind of test; the check at `makiba up` is M4-4's. makiba's own releases take the base's shape (one binary per target, a manifest with each `url` and `sha256`); that belongs to stage 2's installation (plan.md section 2), not to this Issue.
