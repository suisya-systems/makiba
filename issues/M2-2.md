# M2-2 Record status and terminal events

## Before starting

Do not start until probes P1 to P5 are recorded as run, with versions and date, in `docs/design/probes.md` (Results). They are run by hand before any Issue of M2 or M3, on the pinned base version.

## Why

Everything the organization knows about a worker's state comes from what the worker reported, written down as it happened.

## What to build

- `makiba/daemon/monitor.py`: for each event of a terminal carrying `makiba.org`, write `terminal_status`, `terminal_turn` or `terminal_gone` (spec section 10), tied to the run by the `makiba.task_id` tag.
- A status record identical to the last one written for that terminal is not written again.

## Definition of done

The first commit adds `tests/test_monitor.py`, failing, with the trailer `Acceptance-Test: tests/test_monitor.py`. At head it passes and asserts:

- A scripted run `working, blocked(question), working, done` produces exactly those four status events in order.
- A terminal without the organization's tag produces none.
- A terminal that exits produces one `terminal_gone` with its exit code.
