# M4-1 Deny the base's command in every role

## Why

herdr-core does not protect itself from an agent: it has no permission boundary. Whoever reaches it can type into any terminal. The first layer is that no role's settings allow the base's command at all.

## What to build

- `roles/*/settings.json` for secretary, worker and curator: deny rules for the commands, and `Read`, `Edit` and sandbox denies for the folders, that `Base::worker_denies()` lists (spec section 6.2). These are `hc`, `herdr-core`, `herdr-app` and their config and state folders. The same files also deny the person key file for read and write, and the unsandboxed run of a command (`allowUnsandboxedCommands` off), because the person key is what separates the person's verbs from every agent's (spec section 3).
- A `PreToolUse` hook, `makiba hook deny-base` (a subcommand of the one binary, spec section 14), that refuses a Bash command naming one of those commands as a command word or as a path ending in it, fail-closed on unreadable input.
- The rules files say why in one sentence.

## Carried from

## Definition of done

The first commit adds `tests/base_denied.rs`, failing, with the trailer `Acceptance-Test: tests/base_denied.rs`. At head `cargo test --test base_denied` passes and asserts:

- For each role's settings file: every entry of `worker_denies()` is present, and so are the person key file's denies and the switch that refuses an unsandboxed run (a shape test, as paddock's `tests/worker-settings-*.test.sh`).
- The hook refuses the command bare, by absolute path and behind `env`, and passes a command that only mentions the name as an argument.
- The hook refuses on empty and on malformed input.
