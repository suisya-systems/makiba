# M3-3 The door, agent tokens, and the message tools

## Before starting

Do not start until probes P1 to P5 and P7 to P11 are recorded as run, with versions and date, in `docs/design/probes.md` (Results). They are run by hand before any Issue of M2 or M3, on the pinned base version. A probe run in part names the steps not run; those are run before the Issue that relies on them lands.

## Why

Agents must be able to report and to message without being able to write the database. The door is the only thing a sandboxed agent may reach, and it reaches it as tools, because a sandboxed Bash cannot create a Unix socket on Linux.

## What to build

- `makiba/daemon/door.py`: one request handler with two entrances (spec section 3). The Unix socket for the person's `makiba`: one JSON line in, one out. An MCP server on `127.0.0.1:$MAKIBA_PORT` for agents: one tool per verb (spec section 12), the agent's token as the key, and a role listed only the tools of its verbs. Every request recorded in `commands`; `(actor, idem)` returns the first answer again.
- `agents` rows and key checks (spec section 4); verbs allowed per role. A request with no key is `denied`, whatever the peer's user id, process lineage or terminal; on the socket a connection from another user id is refused first. Nothing at either entrance recognizes the person by the absence of a key.
- The person key (spec sections 2 to 4): `makiba/daemon/person_key.py` creates `$MAKIBA_PERSON_KEY` (default `~/.config/makiba/person.key`, mode 0600, in a 0700 folder) when it is absent and stores only its SHA-256 in `agents` (`role = 'person'`). `makiba` sends the content of that file; with no file, it sends no key. `makiba up` (M4-4) calls the creation.
- `makiba/cli.py` with the verbs `send`, `report`, `show`, and the tools of the same names. `report` also moves the run (`report done` sets `review`).
- `makiba` never imports `makiba.db`, except `makiba/status_local.py` (M2-1), which opens it read-only for the person's `status`.

## Definition of done

The first commit adds `tests/test_door.py`, failing, with the trailer `Acceptance-Test: tests/test_door.py`. At head it passes and asserts:

- A request with an unknown key is `denied` and recorded as `rejected`, on the socket and on a tool call.
- A worker's key may `report`; it may not `dispatch`: the worker's tool list has no `dispatch`, and a call to it by name is `denied`.
- The tool list of each role contains exactly the tools of its verbs in spec section 4.
- `send` from a process with no access to `state.db` (the file is made unreadable to the test's CLI call) still results in a `messages` row.
- The message's `sender` is the id bound to the key even when the arguments claim another.
- The same `idem` twice creates one message.
- A request with no key, sent from inside a terminal `makibad` launched (the test agent, calling the socket and the port itself without a token), is `denied` and recorded as `rejected`, for every verb including `config` and `down`. The same holds when the test agent first double-forks and calls `setsid`, so that its parent is no longer the launched terminal.
- A request carrying the person key, sent from a process outside every launched terminal, may use `config`; the same request with a worker's key is `denied`.
- The person key file is mode 0600 in a folder of mode 0700, lies under no worktree and not under the role-files folder, and `state.db` holds only its SHA-256.
- No module of the `makiba` command (`makiba/cli.py` and every module it imports) other than `makiba/status_local.py` imports `makiba.db`; the daemon's own modules (`makiba/daemon/`) do.
