# M3-3 The door, agent keys, and the message commands

## Before starting

Do not start until probes P1 to P5 are recorded as run, with versions and date, in `docs/design/probes.md` (Results). They are run by hand before any Issue of M2 or M3, on the pinned base version.

## Why

Agents must be able to report and to message without being able to write the database. The door is the only thing a sandboxed agent may connect to.

## What to build

- `makiba/daemon/door.py`: the Unix socket of spec section 3; one JSON line in, one out; every request recorded in `commands`; `(actor, idem)` returns the first answer again.
- `agents` rows and key checks (spec section 4); verbs allowed per role. A request with no key is `denied`, whatever the peer's user id, process lineage or terminal; a connection from another user id is refused first. Nothing at the door recognizes the person by the absence of a key.
- The person key (spec sections 2 to 4): `makiba/daemon/person_key.py` creates `$MAKIBA_PERSON_KEY` (default `~/.config/makiba/person.key`, mode 0600, in a 0700 folder) when it is absent and stores only its SHA-256 in `agents` (`role = 'person'`). `makiba` sends `MAKIBA_KEY` when it is set and otherwise the content of that file; with neither, it sends no key. `makiba up` (M4-4) calls the creation.
- `makiba/cli.py` with the verbs `send`, `report`, `show`. `report` also moves the run (`report done` sets `review`).
- `makiba` never imports `makiba.db`.

## Definition of done

The first commit adds `tests/test_door.py`, failing, with the trailer `Acceptance-Test: tests/test_door.py`. At head it passes and asserts:

- A request with an unknown key is `denied` and recorded as `rejected`.
- A worker's key may `report`; it may not `dispatch`.
- `send` from a process with no access to `state.db` (the file is made unreadable to the test's CLI call) still results in a `messages` row.
- The message's `sender` is the id bound to the key even when the arguments claim another.
- The same `idem` twice creates one message.
- A request with no key, sent from inside a terminal `makibad` launched (the test agent, with `MAKIBA_KEY` removed from its environment, writing to the door itself), is `denied` and recorded as `rejected`, for every verb including `config` and `down`. The same holds when the test agent first double-forks and calls `setsid`, so that its parent is no longer the launched terminal.
- A request carrying the person key, sent from a process outside every launched terminal, may use `config`; the same request with a worker's key is `denied`.
- The person key file is mode 0600 in a folder of mode 0700, lies under no worktree and not under the role-files folder, and `state.db` holds only its SHA-256.

## Notes

Probe P1 has been run before this Issue starts. It measures what this Issue's test cannot: whether a real sandbox lets the agent reach the door, and not the base and not the person key file. The test here shows that the door asks for a key and takes none from lineage; that a sandboxed worker cannot read the person key is P1's and M4-5's to show. If the door cannot be reached, this Issue's transport becomes a spool folder; the request and response shapes stay. If the person key can be read from the sandbox, the plan stops for a decision (probes.md, P1).
