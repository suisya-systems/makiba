# M0-3 A stand-in for the base, and the real base for CI

## Why

claude-org-ja's workers cannot start a herdr-core inside their sandbox (paddock inventory, section 2: `cannot start core: Read-only file system`). Workers need something to test against locally; CI needs the real thing.

## What to build

- `src/base/stub.rs`: an in-process implementation of the `Base` trait (spec section 6.1) with scripted terminals. It is the reference for what the interface means.
- `tests/common/mod.rs`: a `base()` helper the tests share. By default it returns the stand-in. With `MAKIBA_TEST_REAL_BASE=1` it starts the real base in a place of its own (`HC_SESSION=makiba-test-<pid>` and scratch XDG folders) and stops only that, when the returned value is dropped.
- CI runs the suite twice: `cargo test --locked` with the stand-in, and again with `MAKIBA_TEST_REAL_BASE=1`.
- A check that a real-base run never touches the place a person works in.

## Carried from

- paddock: `tests/hc-stub.sh` (as a reference for which behaviours a stand-in needs, not as code)

## Definition of done

The first commit adds `tests/base_fixture.rs`, failing, with the trailer `Acceptance-Test: tests/base_fixture.rs`. At head `cargo test --test base_fixture` passes and asserts:

- The same test (launch a terminal that prints a line, read the line, end it) passes on the stand-in and on the real base.
- With the real base, the fixture's place is never the default one and its folders are under a temp dir.
