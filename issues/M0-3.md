# M0-3 A stand-in for the base, and the real base for CI

## Why

claude-org-ja's workers cannot start a herdr-core inside their sandbox (paddock inventory, section 2: `cannot start core: Read-only file system`). Workers need something to test against locally; CI needs the real thing.

## What to build

- `makiba/base/stub.py`: an in-process implementation of the `Base` interface (spec section 6.1) with scripted terminals. It is the reference for what the interface means.
- `tests/conftest.py`: a `base` fixture. By default it yields the stand-in. With `MAKIBA_TEST_REAL_BASE=1` it starts the real base in a place of its own (`HC_SESSION=makiba-test-<pid>` and scratch XDG folders) and stops only that.
- CI runs the suite twice: once with the stand-in, once with the real base.
- A check that a real-base run never touches the place a person works in.

## Carried from

- paddock: `tests/hc-stub.sh` (as a reference for which behaviours a stand-in needs, not as code)

## Definition of done

The first commit adds `tests/test_base_fixture.py`, failing, with the trailer `Acceptance-Test: tests/test_base_fixture.py`. At head it passes and asserts:

- The same test (launch a terminal that prints a line, read the line, end it) passes on the stand-in and on the real base.
- With the real base, the fixture's place is never the default one and its folders are under a temp dir.

## Notes

Probe P2 (docs/design/probes.md) decides whether the real base can run in GitHub's CI. If it cannot, this Issue ships the stand-in half and says so in `docs/design/probes.md`.
